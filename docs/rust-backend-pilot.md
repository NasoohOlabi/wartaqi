# Draft Rust backend migration

The migration targets a complete local Rust backend for the existing React app and its same-origin HTTP and Socket.IO client. The current candidate serves the workspace relay, notebook reads and writes, browser phone sign-in and device accounts, profile and password updates, diagnostics and the student Telegram API. Bun and Rust share the existing Postgres session format and private signing key. The full-backend performance comparison follows complete local behavior parity. The early container comparison below covers the routes both backends supported at the time.

## What the repository does today

| Boundary                      | Current behavior                                                                                                                                                                                                                                                                                                                                    | Porting implications                                                                                                                                                  |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace change stream       | Postgres statement triggers on six domain tables send a transaction-bound, empty `NOTIFY`. Each Bun process has one dedicated listener and broadcasts an empty `workspace:changed` Socket.IO event. The React client shares the connection, coalesces hints and repairs missed updates on reconnect, foreground and a 30-second visible-page timer. | Small extraction. Keep the existing triggers, Socket.IO polling and WebSocket upgrade, and the same-origin path. A reconnected database listener sends a repair hint. |
| Notebook and role projections | Hint recipients fetch role-checked views. `functions/notebook-service.ts` owns account/assignment checks, SQL transactions and response shapes. The Student response projects only the linked student's attendance.                                                                                                                                 | Read-only endpoints can be ported one at a time. Preserve row ordering, error responses, access checks and the visibility of legacy, cleared and reversed marks.      |
| Offline writes and grades     | React persists queued operations in IndexedDB. Bun reconciles them with current Postgres values, appends events and stores grade receipts. The database sequence determines event order.                                                                                                                                                            | High parity burden. Compare results and durable effects when an acknowledgement is lost, operations are repeated, or another device edits the same record.            |
| Identity and integrations     | Bun hosts Better Auth, phone/password and device account sessions, invitations, MCP OAuth and the private Telegram API. The Telegram worker deploys separately.                                                                                                                                                                                     | Keep the shared signing key, credential hashes, session tables and integration endpoints compatible through cutover.                                                  |

Entry points are [Bun's HTTP server](../server/index.ts), [its relay](../server/sync.ts), [the SQL triggers](../neon/019-workspace-invalidation.sql), [the React subscriber](../src/syncStream.ts), [the notebook API](../functions/notebook-service.ts) and [the ledger projection](../shared/ledger.ts).

## Run the relay and parity test

The candidate lives in `rust-sync/`, with its own Cargo lockfile and Docker build context. It serves `GET /health`, `/socket.io/` and the ported HTTP endpoints. The socket handshake checks the session and the current application grant. Rust listens on the existing Postgres channel and broadcasts the same empty hint. React keeps its local queue and existing request paths.

Use a disposable local Postgres and apply `railway/*.sql` then `neon/*.sql` in filename order, as in [CI](../.github/workflows/ci.yml). With the repository's Bun dependencies installed, run these PowerShell commands from the root. Use the actual port and database name for your disposable instance.

```powershell
cargo build --locked --release --manifest-path rust-sync/Cargo.toml
$env:TEST_RAILWAY_DATABASE_URL = 'postgres://postgres@127.0.0.1:5432/notebook_test'
$env:TEST_RUST_SYNC_BINARY = (Resolve-Path rust-sync/target/release/wartaq-workspace-relay.exe).Path
bun test tests/sync-transport.test.ts tests/rust-backend-parity.test.ts
```

On Windows, use `cargo +stable-x86_64-pc-windows-gnu` if your Rust toolchain uses MinGW instead of the MSVC linker. On Linux, omit `.exe` from the binary path.

Both cases exercise the official JavaScript client against a real Bun instance and the same synthetic Postgres fixture. The Rust case routes only the socket traffic to Rust. The contract covers direct WebSocket, polling, upgrade, missing cookie, invalid identity, invitation setup, foreign origin and cross-site requests, transaction rollback, ignored diagnostics, committed writes, listener loss and fresh access denial after grant revocation. It compares statuses, errors and event arguments where they are part of the app contract. Session IDs, connection IDs and heartbeat timings are implementation-generated. The existing wider [sync verification matrix](sync-verification.md) remains the release gate for any future transport switch.

Raw malformed Engine.IO requests can differ. For example, Rust checks for a cookie before the transport library validates an invalid query, while Bun validates the query first. Standalone mode's `/health` checks process liveness. The transport test independently verifies the Postgres subscription. The Chromium scenario with `TEST_RUST_BROWSER_BINARY` forwards all traffic to the hybrid executable. Rust serves the built assets and selected native reads. The loopback Bun process handles phone sign-in, device-account changes and attendance writes. See the [runtime map](rust-architecture-audit.md) when interpreting a passing test. Complete the browser suite and verify readiness and rollback before any deployment.

The HTTP comparison uses the same sessions and fixtures for both backends. It checks statuses, response headers and JSON for all three roles. The suite includes rejected requests, enrollment visibility, legacy marks, malformed ledger data, transactional rollback, and retries across runtimes for grades, attendance, notes, phone numbers, and profiles. Staff course sorting uses Postgres's `en-US-x-icu` collation. Canonically equivalent names and differences between Postgres and Bun's ICU versions need additional parity coverage.

For a local launch, set `PORT` (defaults to `3001`), `WORKSPACE_ORIGIN` to the browser-facing origin, `DATABASE_URL` to the disposable database, and `BETTER_AUTH_SECRET` to the shared private key. Set `ASSET_DIR` to the built React `dist/` directory for same-origin asset serving. Use `BUN_ORIGIN` if running the session verification bridge without a signing key. For a container build use `docker build -t wartaq-rust-sync rust-sync`. The Postgres connection uses plaintext, so use loopback or an isolated private network. An eventual trial can route individual proven paths to Rust through the same public origin and restore their Bun routes for rollback.

## Early local container comparison

Both app containers ran with a 1-vCPU quota, identical synthetic database copies and 12 connected Socket.IO clients. At 20 requests per second, each completed 600 requests across two trials. Average app CPU per request was 17.74 ms for Bun and 2.93 ms for Rust. App resident memory was 196.1 MiB and 9.6 MiB respectively. The two-trial average p95 was 43.7 ms for Bun and 103.4 ms for Rust.

At 75 requests per second, Bun completed both 900-request trials. Rust had 201 failed or timed-out requests in one trial and completed the other. These measurements cover notebook, student and account reads, attendance sync writes, and notifications on an internal Docker network. The local driver, sampler, and per-trial results are under `.artifacts/local-profile/`.

## Migration sequence

The current slice ports browser sign-in, device accounts, profile and password updates, invitation setup, remaining catalog writes, Telegram student access and transcript diagnostics. The Telegram crate covers polling and encrypted state. MCP discovery, selected tools and teacher credential checks run in Rust tests. Account administration, the Telegram conversation handlers, native MCP transport and OAuth are still open.

1. Finish the notebook and browser account lifecycle in Axum. Keep the existing Postgres schema, transactions, session signing and credential hashes. Test phone sign-in both ways across runtimes, remembered accounts, password changes, invitation redemption, account administration and revocation. Run writes against independently seeded fixtures and compare response statuses, headers, decoded JSON and durable effects. Exercise exact and conflicting retries, legacy events, concurrent edits, and role scope.
2. Port MCP discovery, consent, OAuth and tools. Use the [official Rust MCP SDK](https://github.com/modelcontextprotocol/rust-sdk) for Streamable HTTP and wire authorized calls to the same Rust notebook operations as the web API. Preserve registered clients, PKCE and redirect requirements, audience, DPoP binding, token rotation and revocation. Replay the existing MCP clients and tests on both services, including invitations, negotiated protocol versions and forbidden cross-account operations.
3. Port the separate Telegram process with [Teloxide](https://github.com/teloxide/teloxide) for the Bot API. Keep long polling and make the application own the durable offset and update receipts. Preserve the SQLite volume and encrypted state across restarts and runtime switches. Replay message and callback updates against a fake Telegram Bot API, then compare outbound replies, retries, account linking, attendance, grading, exports and Arabic and English menus. Use a synthetic model endpoint for assistant traces, follow-ups and confirmation before writes. Verify the complete flow from linking to revocation against the Rust app APIs.
4. Boot the Rust app and Telegram worker locally with Bun absent from the runtime path. Serve the same built React assets and use the current URLs, cookies and Socket.IO path. Run the browser suite and integration contracts against both runtimes. Include listener and DB outages, mobile offline recovery, duplicate Telegram updates, restart with persisted state, and a return from Rust to Bun on the same database and worker state.
5. When standalone parity is green, rerun the isolated container comparison with identical limits and fixtures. Compare CPU and memory for the app, worker and Postgres, p95 and p99 latency, errors, SQL query counts and notification delivery. Repeat the 75 requests per second trial to diagnose the prior Rust failures before using the benchmark for a cutover decision. Keep all load on local containers.

## Rehearse cutover and rollback locally

Build both candidates from recorded commits. Start the Rust app on an alternate address and run database, listener and static asset readiness checks. Keep the public origin, signing secrets, Postgres URLs, cookie names and frontend routes fixed throughout the exercise. Stop the Bun Telegram poller before starting its Rust replacement on the same worker state. Both app versions must understand sessions and writes from the other runtime before switching the ingress route.

After the switch, check phone sign-in, one permission-scoped write and its socket delivery, reconnect repair, MCP discovery and one token exchange, and a Telegram reply. For rollback, restore ingress to the recorded Bun build and switch the Telegram poller back in the same stop-then-start order. Preserve all committed Postgres writes, OAuth state and the latest Telegram offset during rollback. Record recovery time and any duplicate or missing events observed in the rehearsal.

The first production rollout uses the existing web service. Rust serves the React assets, sockets and selected GET routes, while a local Bun process handles the remaining requests, including all grade writes and MCP. The Telegram worker continues to run Bun. The earlier container figures describe the standalone candidates. Measure the deployed combination separately and complete the local parity steps above before retiring Bun. See the [web runtime and rollback procedure](railway-setup.md#web-runtime-and-rollback).

Railway charges for runtime CPU and memory, and service builds are free. A second always-on process adds its own memory use and a Postgres connection. The empty Socket.IO hint is cheap to send. A full role projection or a periodic refresh can cost more, so measure both application and database work before making a savings estimate. Railway can collect CPU and memory metrics per service, while application latency and parity need workload instrumentation.
